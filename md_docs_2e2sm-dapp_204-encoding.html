E2SM-DAPP: encoding

This chapter describes how an implementation turns every E2SM-DAPP information element into bytes. It gives worked examples that an implementer can check against the reference test vectors, the size limits and the type map.

The index is README.md. The field lists are in 02-ie-mapping.md. The validation rules are in 05-semantics-and-constraints.md. Code references, product names and build switches are in integrator-guide.md.

What is on the wire

An implementation shall encode each E2SM-DAPP information element as one ASN.1 value with APER (ASN.1 Packed Encoding Rules, aligned variant, X.691). It shall carry the value as the content of an OCTET STRING in the E2AP message. E2AP does the framing. E2SM-DAPP adds no header, no length prefix, no checksum and no version byte of its own.

Table: ASN.1 type that each E2AP field carries

E2AP field that carries it ASN.1 type that is encoded into it

RIC Event Trigger Definition (RIC Subscription Request) E2SM-DAPP-EventTrigger
RIC Action Definition (RIC Subscription Request) E2SM-DAPP-ActionDefinition
RIC Indication Header (RIC Indication) E2SM-DAPP-IndicationHeader
RIC Indication Message (RIC Indication) E2SM-DAPP-IndicationMessage

The grammar is in the last clause of this chapter. Its module identifier is E2SM-DAPP-IEs {... oran(53148) e2(1) version1(1) e2sm(255) e2sm-DAPP-IEs (3)}, so the OID is 1.3.6.1.4.1.53148.1.1.255.3.

Plain and FlatBuffers encodings do not exist. A conforming stack encodes APER. Some implementations ship unused stubs for the other encodings.

The three rules that decide almost every byte

  1. Alignment. In aligned PER a value that needs whole octets (an integer longer than a byte, an octet string, a character string, a length determinant of more than 8 bits) first skips to the next octet boundary. The skipped bits are zero. Bit fields (extension bits, presence bits, small counts, choice indices) are not aligned and are packed MSB first.
  2. Every SEQUENCE and CHOICE here has an extension marker (...), and so do the constrained integers except data-size. An encoder always writes the extension bit as 0. Each marker costs one bit.
  3. OPTIONAL fields cost one presence bit each, written before the first component, in the order the fields are declared. A cleared bit means the field is absent and takes no further space.

SEQUENCE (SIZE(1..1)) OF no bits for the count control style list

Notes on the table.

  • Unbounded integers are not 32-bit. A RIC-Style-Type of 4294967295 (the largest value of a 32-bit unsigned integer) needs five octets on the wire, because the top bit of 0xFF would otherwise read as negative: 00 ff ff ff ff. See vector ad_style_max below.
  • Timestamps are 8 octets for any value in this century. A nanosecond timestamp since 1970 is about 1.7e18, which needs 61 bits, so it is 08 followed by 8 octets. The largest value the grammar can hold in all the implementations is 2^63 - 1, 08 7f ff ff ff ff ff ff ff.
  • Octet-string content is never bit-shifted. Because octet strings are aligned, the payload inside data and e3-control-outcome is byte-identical to what the sender passed in. A receiver can hand a pointer into the E2SM-DAPP buffer to the inner decoder.
  • The outer E2AP OCTET STRING length is E2AP's, not E2SM-DAPP's. The encoded length of an E2SM-DAPP element is whatever the APER value occupies, rounded up to a whole octet (see the single-byte examples below).

Byte order, packing, length prefixes

Table: Byte order, padding and length prefixes

Topic Rule
Byte order APER is a bit stream, written most significant bit first. Multi-octet integers and lengths are big-endian. There is nothing host-endian on the wire.
Padding Encoders write zero pad bits. The last octet is padded with zero bits to a whole octet.
Struct packing None on the wire. Native structures in memory are the implementation's own business.
Length prefixes Only where the table above says so. E2SM-DAPP never prefixes a whole element with its length.
Extension markers Written as 0. The next subsection says what a receiver does with 1.
Trailing data APER has no end marker. A decoder checks that the decode succeeded. It does not need to check that it consumed every octet, and several implementations ignore trailing octets. A receiver should not rely on a sender to append nothing.

A receiver that sees extension additions

The grammar has no extension additions yet, so every extension bit that a conforming sender writes is 0. A future version could add fields after the ... marker. A decoder that meets extension bit 1 has three options, and implementations pick differently.

Table: Handling of extension bit 1 on a SEQUENCE

Implementation Extension bit 1 on a SEQUENCE
A (generated codec) The decoder reads the extension bitmap and skips additions that it does not know. The value decodes with the added fields ignored.
B (hand-written codec) The decoder reads the additions as opaque open types (X.691 19.7 to 19.9) and drops them. The encoder refuses a structure with the extension flag set.

A CHOICE alternative beyond the defined ones (a future format 3) is not skipped by any implementation. The decode fails.

An extension bit of 1 on a constrained INTEGER (0..4294967295, ...) means that the value is outside the root range and uses a different encoding. Implementations reject it. See 05-semantics-and-constraints.md.

Format 2 is the one element that can be larger than 32768 octets, because the grammar bounds only the number of items, not the encoded size of the list.

Implementation limits are tighter than the grammar. An implementation can encode into fixed buffers and fail when an element does not fit. The buffers range from 1 KiB for an action definition to 512 KiB for an event trigger, and one implementation limits a control message to about 16 KiB, although the grammar allows 32768 octets. For this reason the reference test vector cm1_large stops at 16000 octets. A sender that wants to work with every implementation should keep a control message below 16 KiB. The details are in integrator-guide.md.

All 31 vectors (27 inline and 4 by length and hash) were also reproduced by an independent bit-level encoder, which agreed byte for byte.

Two APER layers nest in the control outcome

e3-control-outcome is an OCTET STRING, and the Spectrum Service Model fills it with its own APER encoding of Spectrum-ApplyOutcomeData (02-ie-mapping.md). So a received outcome has two independent APER values, one inside the other:

E2SM-DAPP-ControlOutcome (APER, this specification)
timestamp, sequence-id
e3-control-outcome OCTET STRING (octet-aligned, copied as is)
Spectrum-ApplyOutcomeData (APER, owned by the Spectrum Service Model)

The inner value starts on an octet boundary and its bit alignment is its own: it is decoded from its first octet as if it were a standalone message. The same tunnel is used by ControlMessage-Format1.data (xApp to RAN) and IndicationMessage-Format1.data (RAN to xApp).

Properties that these vectors pin down:

  • The all-ones values (4294967295, INT64_MAX) and the minimum values (0) of every bounded and unbounded integer.
  • An absent versus a present optional field, in each combination for the outcome.
  • The smallest and largest legal payloads of both message formats (the control message stops at 16000 because of the buffer limit of one implementation).
  • A subscription list of 0, 1, 2, 255 and 256 items.

The vectors do not cover: extension bit 1, a ranFunction-Instance, an e3-control-outcome longer than 127 octets (two-octet length form), a PLMN that is not three bytes, a timestamp with the top bit set, and any invalid input.

Native types for the grammar types

Implementations hold the grammar types in different native types. This clause lists the typical choices and the traps. Field names in the C++ and the C structures of a codec can follow the grammar names exactly, so that the same names work across implementations.

Table: Typical native types for the fields

ASN.1 field Typical native type Note
ran-function-id, dapp-id, node-nb-id (0..4294967295) unsigned 32-bit or 64-bit integer Use 64 bits when 4294967295 shall stay positive in a signed language.
node-type (0..255) unsigned 8-bit integer
node-plmn-id (SIZE(3)) array of 3 octets
node-cu-du-id OPTIONAL presence flag and an unsigned integer
timestamp OPTIONAL presence flag and a signed 64-bit integer One implementation treats 0 as absent.
sequence-id OPTIONAL presence flag and a signed 64-bit integer One implementation treats 0 as absent.
data-size (0..32768) unsigned 16-bit integer Some implementations drop the field and use the length of data.
data octet string, size 1..32768
e3-control-outcome OPTIONAL presence flag and an octet string with no bounds One implementation treats a null pointer and a size of 0 as absent.
ric-style-type, format and style types signed 64-bit integer The grammar has no bounds for these types.
ranFunction-Instance OPTIONAL presence flag and a signed 64-bit integer One encoder rejects a present instance.
the format choice enumeration The wire format numbers start at 1.

Two traps:

  • A native format enumeration can start at 0 while the wire format numbers start at 1. The enumeration value is not the RIC-Format-Type that the definition carries, which is 1 and 2. A code that mirrors the enumeration in another language shall use the same numbering as the library.
  • A zero-initialized structure can read as a valid format 1. An all-zero indication message reads as "format 1, no data" when the first enumeration value is 0. An encoder should guard against this.

Checking an encoding

To check a stack, an implementer encodes every input of the reference test vectors and compares the output with the expected bytes. Then the implementer decodes every expected value and compares the result with the input. The checklist and the way to regenerate the vectors are in integrator-guide.md.
