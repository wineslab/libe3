E2SM-DAPP: E2AP information element mapping

This chapter defines every information element of E2SM-DAPP, in the shape of an O-RAN E2SM specification. It shows where each element sits in E2AP. It gives the fields with types, ranges and presence. It lists the formats and styles. It says which E2 service uses which format.

The index is README.md. The bytes of each element are in 04-encoding.md. The message order is in 03-procedure-flow.md. The meaning of the values and the checks on them are in 05-semantics-and-constraints.md.

How to read the field tables:

  • Range is the ASN.1 constraint. A ... after a range is an extension marker on that integer.
  • Presence is optional for an OPTIONAL field. Otherwise it is mandatory.
  • Every SEQUENCE and CHOICE has an extension marker (...). No extension additions exist yet.

2. Which E2 service uses which format

E2SM-DAPP implements two of the E2 services: REPORT and CONTROL. The table lists the report styles and the control style that the RAN advertises. It gives the format that each IE uses under each style.

REPORT 2 E3 subscription map format 1 format 1 format 2 format 2 n/a n/a n/a

Rules for styles and formats:

  • Style numbers. Report style 1 is the E3 data report. Report style 2 is the E3 subscription map. The subscriber chooses the report style with ric-Style-Type in the action definition.
  • Style to format. The RAN function definition carries the style-to-format mapping. It uses ric-IndicationHeaderFormat-Type and ric-IndicationMessageFormat-Type. Style 1 uses 1 and 1. Style 2 uses 2 and 2. The RAN that builds the definition shall fill these in. The definition that a RAN actually sends is authoritative. Test data does not define the standard.
  • Control style number. The control style is 1. The numbering spaces for report styles and control styles are separate in E2SM. The two 1 values do not collide. The control header does not carry a style number. A stack with a second control style needs a new control header format.

  • Style names are free text. RIC-Style-Name is any PrintableString of 1 to 150 characters. The names in use differ by implementation:

    Table: Style names in use

Implementation Report style 1 Report style 2 Control style 1
implementation A (an OpenAirInterface RAN) DAPP-E3-DATA-REPORT DAPP-E3-SUBSCRIPTION-MAP DAPP-CONTROL-STYLE-1
implementation B (test data and a second RAN) E3 Data Report E3 Subscription Map dApp Control
  • Selection by name. Some xApps find the control style by name. They look for the string DAPP-CONTROL-STYLE-1 in the definition. They refuse to send a control if the string is not there. A RAN that works with such xApps shall use that name.

2.1 Why INSERT, POLICY and QUERY are "not used"

E2SM-DAPP defines none of them.

Table: Why the other E2 services are not used

Claim Reason
The RAN function definition has no Insert, Policy or Query section. The grammar of E2SM-DAPP-RANFunctionDefinition lists only name, event trigger, report and control.
An E2 agent accepts only a report action. A subscription with an insert or policy action aborts such an agent.
The E2AP model of an agent has no query action type. The action types are report, insert and policy.
An xApp framework builds only report actions. The action type is report.
Every indication is a REPORT indication. The indication type is always report.
The event trigger needs no timer. The service model answers every subscription with an aperiodic outcome. The RAN drives the reports, not a period.

The reasons were checked in the implementations. The evidence is in the integrator guide.

2.2 Why there is no call process ID

E2AP carries an optional Call Process ID on an indication and on a control request. E2SM-DAPP does not use it.

Table: Why the call process ID is not used

Claim Reason
The agent never sets it on an indication. The indication path fills only the header and the message.
The agent never reads it on a control request. The agent reads only the header, the message and the RIC ID.
The agent writes none on the control acknowledge. The field is absent.
A sender may still put one. One xApp framework sends the string 1 in every control request. The receiver ignores it. A conforming sender omits it.

3. Common types

Several elements use these types.

Table: Common ASN.1 types

ASN.1 type Definition Meaning
RIC-Style-Type INTEGER (unbounded) style number. 1 and 2 for reports, 1 for control. An implementation may store it in 32 bits.
RIC-Format-Type INTEGER (unbounded) format number in the RAN function definition. 1 or 2. An implementation may store it in 32 bits.
RIC-Style-Name PrintableString (SIZE(1..150, ...)) free text
Timestamp INTEGER (unbounded) nanoseconds since the Unix epoch on the realtime clock. In every message it is OPTIONAL. Absent means that the producer did not stamp. That is a normal message.
SequenceId INTEGER (unbounded) correlation id of one detection-to-mitigation procedure. OPTIONAL everywhere. It has the same value as E3-SequenceID of E3AP (INTEGER (1..4294967295)).
SubscribedE3RANFunction-ID INTEGER (0..4294967295, ...) an E3 RAN function id
Bool-Type BOOLEAN defined and never used in the grammar
RANfunction-Name SEQUENCE see the RAN function definition below

The standard has two identifier spaces besides the identifiers of E2. The first is the E3 RAN function id. It says which E3 service model a report or a control belongs to, for example Spectrum. The second is the dApp id. It says which dApp. Both come from the E3 interface. They are not E2 identifiers. The E2 RAN function id of E2SM-DAPP is 255. See 01-identity-and-registration.md.

The E2SM-DAPP ids relate to the E3AP ids as follows. In E2SM-DAPP, ran-function-id and dapp-id are INTEGER (0..4294967295, ...). In E3AP, E3-DAppID is INTEGER (1..65535) and ranFunctionIdentifier is INTEGER (1..65535). Every E3 value is valid in E2SM-DAPP. The reverse is not true. E2SM-DAPP can carry 0 and values above 65535. The E3 link cannot deliver them. See 05-semantics-and-constraints.md.

8. The e3-control-outcome payload

e3-control-outcome is the payload of the control outcome. E2SM-DAPP defines the envelope (the three fields above). It defines nothing about the content. The same tunnelling is used for the control itself (ControlMessage-Format1.data) and for the report (IndicationMessage-Format1.data).

8.1 Who owns what

Table: Ownership of the layers of the control outcome

Layer Owner Defines
E2SM-DAPP-ControlOutcome-Format1 this standard timestamp, sequence-id, and that an opaque payload may follow
the bytes in e3-control-outcome the service model named by the ran-function-id of the control the PDU, its encoding, its units, and what "applied" means for that service model

"Applied" has a different meaning for each service model. For a spectrum control, a PRB block is in effect only after the scheduler puts the mask on the air. That instant is later than the instant at which the control handler returns. For another service model, "applied" can be a single instant, a verdict or a set of counters. E2SM-DAPP cannot say which. It does not try.

8.2 Worked example: the Spectrum service model

The Spectrum service model owns the apply outcome. It does not belong to this standard. The grammar is in the Spectrum specification (E3SM Spectrum). Do not implement the outcome from this document. This section shows what an outcome can contain.

Spectrum defines an apply-outcome PDU, Spectrum-ApplyOutcomeData. It is a SEQUENCE with no extension marker. It has an optional timestamp and an applyOutcomePayload. The payload is a CHOICE with an extension marker. It has one alternative today, prbBlockApplyOutcome. That alternative is a SEQUENCE with an extension marker and four optional fields. Both timestamps are INTEGER values in nanoseconds on the realtime clock of the gNB. The xApp can therefore subtract them from the timestamp of the Spectrum dApp report, which is on the same clock. They are payload fields. They are not latency recorder records, because the latency recorder uses the monotonic clock. Never subtract one from the other. The outcome timestamp is the time at which the outcome was built. The applied instants are in the payload.

maxSlotIndex is 159. It is maxSlotsFrame (160) minus 1.

Table: Fields of the Spectrum apply outcome

Spectrum field Type and range Meaning Absent means
Spectrum-ApplyOutcomeData.timestamp INTEGER when the RAN built the outcome not stamped
installedTimestamp INTEGER the mask was written into the MAC (box B17 in 03-procedure-flow.md) the control was rejected: it never installed
onAirTimestamp INTEGER the first scheduler tick that put the mask on the air (box B18). It is later than installedTimestamp by up to one slot, and by a variable amount. the control installed, but a later install replaced it before any tick ran (it was superseded), or it timed out
sfn INTEGER (0..1023) frame of that tick no tick
slot INTEGER (0..159) slot of that tick no tick

How the RAN fills the outcome:

  • installedTimestamp is present when it is not zero.
  • onAirTimestamp, sfn and slot are present together when onAirTimestamp is not zero.
  • The timestamp is present when it is not zero.
  • The RAN omits the whole payload when neither the installed time nor the on-air time is set. A timed-out control with nothing known is then acknowledged with an outcome that has timestamp and sequence-id and no payload.

A nested example (hand-derived). An outcome was built at 1700000000200000000 ns. The mask was installed at 1700000000100000000. It was on the air at 1700000000103000000, in frame 512, slot 7. The procedure is 42.

Table: Bytes of the nested example

Layer Bytes
inner Spectrum-ApplyOutcomeData (32 octets) 80 08 17979cfe4215c200 3c 08 17979cfe3c1fe100 08 17979cfe3c4da7c0 02 00 07
outer E2SM-DAPP-ControlOutcome (45 octets) 1c 08 17979cfe4215c200 01 2a 20 followed by the 32 inner octets

The inner value reads as follows:

  • Bit 1: timestamp present.
  • The timestamp (08 and 8 octets).
  • Choice extension bit 0.
  • Spectrum-PRBBlockApplyOutcome extension bit 0.
  • Presence bits 1111.
  • Two pad bits, so the octet is 3c.
  • installedTimestamp.
  • onAirTimestamp.
  • sfn 512 as a 2-octet aligned integer (range 0..1023).
  • slot 7 as an 8-bit field (range 0..159).

A superseded control was installed and never on the air. It has presence bits 1000 and ends after installedTimestamp: 80 08 17979cfe4215c200 20 08 17979cfe3c1fe100.

The bytes were derived by hand with the rules in 04-encoding.md. They are not golden vectors. No Spectrum codec was run on them.

8.3 How a consumer reads it

A consumer decodes in two steps. The first step belongs to E2SM-DAPP. The second belongs to the service model.

Step 1, E2SM-DAPP. The consumer decodes E2SM-DAPP-ControlOutcome. It reads four values: the timestamp, the sequence id, the payload and the payload size. A decoder that stores "absent" as 0 gives the consumer a 0. The consumer shall map that 0 back to "absent" for the timestamp and the sequence id. When the E2AP outcome field is empty, or the decode fails, the consumer shall treat all four values as absent.

Step 2, the service model. The consumer passes the payload to the decoder of the service model to which it sent the control. For Spectrum, the decoder returns the installed time, the on-air time, the frame and the slot. Each value can be absent. The frame and the slot are absent unless an on-air time is present.

A decision engine can then compute two latencies from the dApp report timestamp origin:

  • the mitigation latency: the on-air time minus origin;
  • the install latency: the installed time minus origin.

Rules for any consumer:

  1. Treat an absent payload, an empty payload and an undecodable payload as "no values". Never raise an error because of the payload. The acknowledge itself is real.
  2. Use sequence-id from the envelope to find the control that the outcome answers.
  3. Decode with the service model that matches the E3 RAN function id that you put in the control header. The outcome does not say.
  4. Free the payload buffer, if the decoder allocates one.

8.4 How another service model adds its own outcome

A service model with E3 RAN function id N needs no change to E2SM-DAPP. It does the following.

  1. It defines an outcome PDU in its own grammar. It copies the pattern: a SEQUENCE with an optional build timestamp and a CHOICE of outcome payloads. The CHOICE has an extension marker. Alternatives can then be added without a change to the encoding width of the existing one. The Spectrum grammar explains this in its comment on Spectrum-DAppControlPayload.
  2. It makes optional every field that the RAN may not know. "Not known" is then absence, not 0.
  3. In the RAN, when the procedure with sequence-id S ends, it encodes the PDU. It passes the PDU as e3-control-outcome of an E2SM-DAPP-ControlOutcome with the same sequence-id S. If there is nothing to say, it omits the payload.
  4. In the xApp, when the xApp sends a control to E3 RAN function N, it remembers (node, S) -> N. On the acknowledge, it decodes e3-control-outcome with the decoder of N.
  5. It states its clock and units in its own grammar. If it wants the xApp to compute a latency against a dApp report timestamp, both timestamps shall be in nanoseconds on the realtime clock of one host, as the Spectrum ones are.

E2SM-DAPP has no registry of E3 RAN function ids. The RAN stack assigns them. A RIC-side decoder can hard-code the id of a service model. A new service model therefore needs its id agreed between the RAN stack, the dApp and the xApp.
