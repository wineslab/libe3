58/**
59 * @brief E3Interface - Internal protocol coordination
60 *
61 * This class is the internal coordination layer that:
62 * - Manages E3AP lifecycle (Setup, Subscription, Control, Release)
63 * - Owns inbound/outbound processing threads
64 * - Coordinates between connector, encoder, and subscription manager
65 * - Supports simulation mode for testing without real RAN
66 *
67 * This class is NOT directly exposed to library users. Users interact
68 * with the E3Agent facade which owns an E3Interface instance.
69 */

562 /**
563 * @brief Reply to a setup request that cannot be answered positively.
564 *
565 * The RAN side of the setup channel is a REQ/REP exchange: exactly one
566 * reply must be sent per received request before the next one can be
567 * received (a ZMQ REP socket enforces this in its state machine).
568 * Bailing out without replying (undecodable bytes, wrong PDU type)
569 * wedges the setup channel for every subsequent dApp until the agent
570 * restarts. The encoding is fixed and known a priori by both peers, so
571 * a negative SetupResponse can always be produced; the peer gets an
572 * explicit rejection instead of a silent timeout.
573 *
574 * @param request_id Message ID of the offending request, or any id that
575 * cannot be echoed (0 when the request bytes never
576 * decoded, out of E3-MessageID range otherwise) — a
577 * fresh id is then substituted on the wire (dApps do
578 * not correlate setup replies by ID).
579 */
580 void send_negative_setup_reply(uint32_t request_id);

613 */

624 *
625 * Wraps a lock-free counter into the ASN.1 E3-MessageID range, skipping 0.
626 * Monotonic (not random) so an id is unique, letting a caller correlate a
627 * response by the id it was assigned.
628 *
629 * @return The next message id
630 */

634 * @brief Return a request id that can be echoed into a response.
635 *
636 * The decoders do not enforce integer range constraints, so a
637 * peer-supplied message id of 0, outside E3-MessageID's 1..4294967295,
638 * can reach the handlers; echoing it into a response would fail the
639 * encode. Every non-zero id passes through unchanged, 0 is replaced
640 * with a fresh generated id.
641 *
642 * @param request_id Message id a peer sent
643 * @return The same id when it is not 0, a fresh one otherwise
644 */
645 uint32_t sanitize_request_message_id(uint32_t request_id);
