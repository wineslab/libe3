Interoperability

libe3 aims to steer the development of E3AP and to keep the RAN stacks aligned with each other, not only with libe3. In practice:

  • The grammar in this repository (messages/asn1/V1/e3ap-1.0.0.asn1) is the reference. JSON and Protobuf follow it.
  • A change to the wire, or to anything a peer can observe, gets a row in the ledger below and a test or fixture, in the same PR.
  • Where Aerial and OCUDU pull in different directions, libe3 says here which way it goes and why. Where libe3 differs from both, it says so too.
  • A wire that OAI already runs is not changed without a ledger row that says who has to rebuild.

So far libe3 has moved toward its peers on identifier ranges, setup strings, size bounds, the periodicity range and JSON nesting (see the ledger). It holds two things where OCUDU differs, and gives the reasons below: the timestamp stays in the root of the envelope, and E3-ResponseCode stays closed. The sections Aerial and OCUDU say what each stack should change to meet libe3 and the other.

What a libe3 program can expect from other E3 implementations, and a ledger of every change that touched the wire or a peer-visible behavior. This page is the place to look first when libe3 and another stack disagree.

The peers:

  • OAI: the OpenAirInterface E3 agent and the dApp library.
  • Aerial: NVIDIA aerial-sample-apps (dapps v1.1.0, 99b10eb) and its agent in aerial-cuda-accelerated-ran (4f65f97).
  • OCUDU: the OCUDU dApp platform (DeepSig, 38fc00bb526c).

The open differences are tracked in #84, one issue each. This page does not copy them; it says what is settled and what changed.

How sure a statement is:

  • CI means a test in this repository runs it, libe3 to libe3.
  • Source means it was read from the other project's code at the commit above and has not been run.
  • Not run means nobody has tried it.

No peer is run in CI. What CI does check is messages the peers wrote, and the bytes libe3 writes (see Conformance fixtures below); every other cell that names OAI, Aerial or OCUDU is Source or Not run.

JSON as libe3 speaks it

Written by src/encoder/json_encoder.cpp.

Envelope. Every message is one flat JSON object with type, id and timestamp, then the message's own members at the top level. A message with a nested data wrapper is refused. type is the PDU name in camel case: setupRequest, setupResponse, subscriptionRequest, subscriptionDelete, subscriptionResponse, indicationMessage, dAppControlAction, dAppReport, xAppControlAction, releaseMessage, messageAck.

Key names follow the ASN.1 field names: dAppIdentifier, ranFunctionIdentifier, telemetryIdentifierList, controlIdentifierList, subscriptionTime, periodicity, subscriptionId, requestId, responseCode ("positive" or "negative"), sequenceId.

Opaque payloads are nested JSON, not hex. ranFunctionData, protocolData, actionData and reportData carry a JSON object or array. Anything else, an empty payload included, fails to encode with ENCODE_FAILED. Before #118 the first, third and fourth were hex strings; see the ledger.

Granted values. A subscription response carries telemetryIdentifierList, controlIdentifierList, ranFunctionIdentifier and periodicity when the RAN reports them. Absent means not reported; an empty list means none granted. libe3 also reads Aerial's telemetryGrantedList and controlGrantedList as aliases.

The timestamp key is written on every message. It is not in Aerial's schema. Aerial's parsers read by key, so it is expected to be ignored (not run).

libe3 keeps the timestamp where it is (#114). The two placements encode every stamped PDU to different bytes, so OCUDU's native module and libe3 cannot read each other's stamped PDUs, and the move belongs on OCUDU's side. libe3's layout is the one OAI runs, and moving it is a wire change that libe3, OAI's E3 agent and the dApp library would have to rebuild for together. OCUDU's libe3-compatible codec already uses it. Nothing changes in libe3, so there is no ledger row; the ask is in the OCUDU table below.

Because OCUDU reads the number as milliseconds, a libe3 dApp that asks an OCUDU RAN for 100000 (100 ms in libe3 and Aerial) asks for 100 s, which is out of OCUDU's range and rejected. libe3 does not convert: it passes the number through, and the caller facing OCUDU passes milliseconds. OCUDU's libe3-compatible codec does not convert either (it passes the value through and caps it at 1000). Converting on the OCUDU side is the agreed direction (#98).

OCUDU decodes subscriptionTime and never acts on it. That is not a conflict with libe3 or Aerial, which only differ from it in what happens next, but a dApp must not rely on expiry against an OCUDU RAN: a subscription it asked to last 60 s lasts until the dApp deletes it or is released. Until OCUDU changes (see its table below), a dApp that needs the subscription to end has to end it itself, and one that talks to all three can send the time and also delete the subscription when it is done (#95).

Neither libe3 nor Aerial tells the dApp when a subscription runs out. The only message that could, E3-ReleaseMessage, carries just a dAppIdentifier, so it ends the whole session and cannot name one subscription; Aerial's agent sends it only to a dApp that has been idle for 1800 s with no subscription. A dApp that sent a time knows when the RAN will let go. libe3's dApp keeps its own deadline, counted from the response, so it is never earlier than the RAN's and a dApp that renews the moment it passes always reaches the RAN after the old subscription is gone. Aerial's manager counts from the request instead. A libe3 RAN answers a delete for a subscription that has run out negative, as it does for any unknown subscription.

RAN function ids

A function entry in the setup response carries ranFunctionIdentifier, the telemetry and control id lists and an opaque ranFunctionData. It has no name and no version, so on the wire the id is the only thing that says which service model a function is. libe3 does not interpret it.

Id Service model Served by
1 Spectrum OAI
2 NVIDIA L1 KPM Aerial's agent, which accepts no other id, and OAI, whose L1 KPM is built to be wire-compatible with it and advertises a subset of the telemetry ids (1, 4, 5 and 6 of Aerial's 25)
10, 11 Telemetry, management (OCUDU-TELEMETRY-SM) OCUDU

Id 2 is one service model on both stacks, not two that happen to share a number, so a dApp written for Aerial connects to OAI unchanged. The agreement lives in the two codebases, not in the protocol: nothing on the wire says "NVIDIA L1 KPM, version 1", and libe3 cannot check it. OCUDU's entry has an optional ranFunctionName and ranFunctionVersion for this. libe3's has neither, and RanFunctionDefinition::sm_name and sm_version are declared but never sent. Carrying a name and version would let a dApp verify the id, and tell apart two services that pick the same number later. It is not done; #87 records it. Until then a dApp should treat an id as an agreement with the RAN's vendor, not as something it can verify.

All rows are Source, not tested: OCUDU at dApp platform 38fc00bb526c, Aerial and OAI at the commits cited on #87. The telemetry ids OAI advertises are as stated there.

Conformance fixtures

What CI checks against messages or bytes that did not come from the code under test. Added in #102.

Aerial, JSON. tests/fixtures/aerial/e3_message_examples.json is NVIDIA's own example file, copied unchanged from aerial-sample-apps 99b10eb (tests/fixtures/README.md says how to update it). tests/test_interop_aerial.cpp decodes all 17 messages in it and re-encodes each. They cover nine of libe3's eleven message types; Aerial publishes no dAppReport or xAppControlAction. The differences the test pins, so neither side can change them silently:

  • Aerial sends no timestamp; libe3 reads it as 0 and writes one.
  • Aerial's subscription response names the granted lists telemetryGrantedList and controlGrantedList; libe3 reads them and writes telemetryIdentifierList and controlIdentifierList.
  • A negative reply carries a free-text message, and a negative setup response has no ranIdentifier; libe3 reads the text as detail and writes detail, with a cause, never message, and reads the missing identifier as empty.
  • An indication carries a subscriptionId and a messageAck a dAppIdentifier; libe3 reads neither.
  • ranFunctionData is a JSON array in Aerial's setup response; libe3 keeps it as it came.

libe3, ASN.1. tests/test_asn1_golden.cpp pins the APER bytes of one PDU per message type, in the shape OCUDU keeps (id 42, timestamp 1756800000123456789), so OCUDU can re-pin against them. A change to those bytes is a wire change and needs a ledger row. The same file checks that the 11 PDUs OCUDU recorded from libe3 0.1.3 are refused with DECODE_FAILED.

Not covered: anything from OAI, and any live Aerial or OCUDU agent.

When the RAN goes away

What a libe3 dApp sees, and what each peer does to cause it. Added in #120.

Peer What it does What the libe3 dApp reports
Aerial Sends a releaseMessage naming the dApp, for example after 1800 s idle RELEASED_BY_RAN
OCUDU Closes the association (idle 30 s, setup timeout, release, bad PDU); sends no release to a dApp CONNECTION_LOST
Any Socket closed, link failed, ZMQ heartbeat missed CONNECTION_LOST

The dApp does not reconnect. The program calls stop() then start(), or exits (#121). A dApp that sent its own release() gets no event when the RAN then closes.

What that means on the wire, checked by encoding the same values with the grammar of the later revision and with E3SM-SPEC:

  • A dApp report, a sensing indication, a cell configuration indication, an apply outcome and an xApp control of either alternative have the same octets in both grammars.
  • A PRB block control with neither optional field has the same octets in both. A control with one of them does not: E3SM-SPEC has one presence bit where the later revision has two, and its validityPeriod has a length field. The table below gives examples.
  • In Protobuf and JSON, validity_period and validityPeriod keep their field number and key, and the unit changes. A value of 60 from a sender of the later revision means one minute. A receiver of E3SM-SPEC reads it as 60 ms.
  • In Protobuf, a receiver of E3SM-SPEC skips field 2, sampling_threshold, as an unknown field. In JSON it ignores the key samplingThreshold.
  • A sensing policy control without validityPeriod has the same octets in both grammars. It is the first extension alternative in both. With a validityPeriod the field is wider in E3SM-SPEC. The open type keeps the error inside the alternative: the later revision reads 60000 ms as 16619, and E3SM-SPEC reads 60 s as 60 ms.
  • A sensing reservation or PUSCH slots control of the later revision is an extension alternative that E3SM-SPEC does not know. A receiver rejects it (clause 9).
  • The indication of the first revision is a bare Spectrum-SensingIndication. A receiver of the later revisions decodes protocolData as Spectrum-Indication, so the two do not interwork.
  • A RAN of the first revision cannot send an apply outcome.

E2SM-DAPP

E2SM-DAPP carries dApp traffic between an E2 node and an xApp. The specification names the implementations by letter, and so does this subsection:

  • A, flexric: the original C implementation of the service model, in an E2 agent and a RIC library.
  • B, libe3: the C++ and C codec that ships with this repository.
  • C, OCUDU: a C++ RAN stack with a hand-ported codec.
  • OAI: the RAN bridge described in reference [i.2] of the README.
  • An xApp framework: a Python framework that wraps flexric.

File names, line numbers and code roots for each entry are in the integrator guide and code pointers. Nothing here is a design decision; those are in the specification.

Severity: abort means an assertion or equivalent takes the process down in a build with assertions on. wrong means a wrong result with no error. latent means only a corner case triggers it. doc means documentation only.

2. Where the grammar and the implementations disagree

# What Effect
2.1 data-size duplicates the octet string length in IndicationMessage-Format1 and ControlMessage-Format1. flexric writes its own data_size into both the ASN.1 field and the octet string length. On decode it takes the size from the octet string and ignores the ASN.1 field. libe3 and OCUDU keep the ASN.1 field as its own value on encode and decode. They check neither against the octet count A sender that writes different values is read as the octet length by flexric and as the field by libe3 and OCUDU. wrong. Always send equal values
2.2 The grammar allows 0..256 dApps and 1..64 functions per dApp. flexric accepts fewer. Its decoder, its encoder for the report and control item lists, and its list helpers assert on 256 dApps and on 64 functions. The generator of the reference test vectors documents this A list of 256 dApps, a list of 0 items in a definition, or a dApp with 64 functions aborts flexric. The indication message format 2 path tolerates an empty list. It does not tolerate 256 items on decode. abort
2.3 The definition item lists. flexric checks 0 < n < 64. The grammar allows 1 or 2 report styles and 1 control style flexric accepts what the grammar forbids and leaves the rejection to the ASN.1 runtime
2.4 ranFunction-Instance is in the grammar and unusable in flexric. Its encoder asserts that the instance is absent. Its decoder never reads it A definition with an instance is lost on decode and cannot be encoded. libe3 and OCUDU support it
2.5 RIC-Style-Type and RIC-Format-Type are unbounded INTEGER. flexric stores 32 bits A style above 4294967295 or a negative style cannot be represented. libe3 and OCUDU hold 64 bits. latent
2.6 Timestamp and SequenceId are unbounded INTEGER. Every implementation holds 64 bits A value that needs more than 8 octets cannot be decoded. OCUDU rejects it. libe3 checks that it fits
2.7 node-plmn-id is OCTET STRING (SIZE(3)), not the 3GPP PLMN-Identity. OAI writes the digits as three shifted values. This drops a digit of a three-digit MNC and is not BCD A consumer cannot read the PLMN without knowing the packing of the RAN. The grammar does not define a packing
2.8 The dApp E3 subscription list may be empty (SIZE(0..256)). A subscription item needs at least one function. The report and control item path of flexric needs at least one item OAI omits the field when no dApp has a function. An empty list in indication message format 2 is legal and works
2.9 E2SM-DAPP ids are 0..4294967295. E3AP ids are 1..65535 Values that E3 cannot carry are legal in E2SM-DAPP. The reference test vectors include them
2.10 SequenceId is unbounded. E3-SequenceID is 1..4294967295. The control path has no range check. flexric converts a signed value to an unsigned key. OAI truncates it to 32 bits An id above 2^32 - 1 or a negative id makes the parked key and the completion key differ. The relay never completes the control. The 150 ms timeout of OAI retires it. latent
2.11 The OID text. The grammar and the string use e2sm(255). One comment uses e2sm(2) Stale comment. doc
2.12 The grammar file in flexric has a v0 in its name and its module is version 1 The v0 does not mean a version 0 grammar. The grammar files of flexric and libe3 are byte-identical. doc
2.13 The control header carries no style number This works while there is one control style. A second control style needs a new header format
2.14 The control outcome carries no ran-function-id The xApp shall remember the E3 RAN function per sequence-id to decode the payload. See 02-ie-mapping.md
2.15 An absent timestamp or sequence-id is not an error in the grammar. In flexric, 0 means absent flexric cannot send a present 0. See 05-semantics-and-constraints.md

3. Aborts and error handling in flexric

# What
3.1 Every decoder asserts a successful decode. A malformed or truncated PDU aborts the process
3.2 The encoders of the event trigger, action definition, control header, control message, control outcome and definition assert instead of returning an error. Only the encoders of the indication header and message return an empty buffer
3.3 A control request without "ack requested" aborts the E2 agent
3.4 A subscription with more or fewer than one action, or with an insert or policy action, aborts the agent
3.5 An unknown report style. OAI returns an empty answer, then an assertion of the agent aborts
3.6 A deferred control with key 0 aborts the agent. The service model defers on whatever sequence-id the header holds, and the table asserts that it is not 0. OAI avoids this by answering at once when the id is 0
3.7 The inner decode on the RIC side asserts. A format 1 indication whose ran-function-id has no decoder aborts the xApp. Only id 1 (Spectrum) is known. An unknown indication format aborts too
3.8 The control path on the RIC side aborts when it cannot encode the inner control payload. It returns an empty request without error when the E3 type is "none" or the message already carries data
3.9 The RIC Service Update handler on the RIC side does not decode the new definition
3.10 The first RIC Service Update repeats the revision of the E2 Setup. The trigger also finds the service model by the literal 255. wrong
3.11 A comment says that unanswered controls are acknowledged "negatively". The sweep sends a RIC Control Acknowledge with no outcome. doc
3.12 Two parked controls with the same key. A completion releases one. The other waits for a sweep that nothing runs (see 1.6)
3.13 A fixed encode buffer means that large elements abort. The sizes are 512 KiB for the event trigger, 1 KiB for the action definition, 1 KiB for the indication header, 128 KiB for the indication message, 16 KiB for the control header, control message and control outcome, and 16 KiB for the definition. A control message above about 16 KiB aborts although the grammar allows 32768. The reference test vector for a large control message stops at 16000 octets. A definition with the map for 256 dApps of 64 functions each (about 83 KiB per copy, listed twice) does not fit either
3.14 The clock helper returns -1 on error and OAI uses it unchecked
3.15 OAI does not clamp the dApp list to the grammar. More than 256 dApps, or a dApp with more than 64 functions, would reach flexric's encoder
3.16 The equality helper of the event trigger compares the format of the first argument only. latent (there is one format)

6. What the reference test vectors prove and what they do not

  • They prove that libe3 and OCUDU encode every listed input to the exact bytes of flexric and decode those bytes back (see the integrator guide).
  • flexric produces them, so they inherit its limits. There is no present 0, no ranFunction-Instance, no control message above 16000 octets, no e3-control-outcome longer than 10 octets and no extension bits.
  • They say nothing about invalid input. Section 5 lists the places where the three codecs differ on it.
  • The expected behavior on extension bits, trailing octets and outcome payloads above 127 octets (two-octet length form) comes from ITU-T X.691 and the ASN.1 runtime. It does not come from a vector.
