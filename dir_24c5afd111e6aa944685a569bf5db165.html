e2sm-dapp Directory Reference

Detailed Description

E2SM-DAPP

E2SM-DAPP is the E2 service model that carries dApp traffic between an E2 node (a RAN) and an xApp. The RAN relays each dApp report to the xApp as a RIC Indication. It relays each xApp decision to the dApp as a RIC Control. The acknowledge reports what applying the decision did on the air.

This directory is the specification of the service model: the grammar, what the fields mean, and the encoding. A RAN or an xApp written from this text can interoperate with any other. The integrator guide is not part of the specification. It holds the pointers to code and artifacts.

Scope

The present document specifies the E2 Service Model (E2SM) "dApp" (E2SM-DAPP) for the RAN function that relays the traffic of dApps between an E2 node and a Near-RT RIC.

The RAN function offers two RIC services:

  • The REPORT service delivers the reports of dApps to the xApp, and the map of the dApps that are connected to the E2 node.
  • The CONTROL service delivers the decision of the xApp to the dApp, and returns the outcome of applying it.

The present document defines the RAN function definition, the information elements and the procedures of this service model. It also defines the APER encoding of the information elements and the handling of unknown and erroneous data.

Terms, symbols and abbreviations

Terms

For the purposes of the present document, the terms and definitions given in O-RAN WG3.TS.E2GAP [1], O-RAN.WG3.TS.E2SM [3] and the following apply.

  • dApp: an application that runs next to the E2 node and talks to it over E3.
  • dApp E3 subscription map: the list of the dApps connected to the E2 node, each with the E3 RAN functions it has subscribed to.
  • E3 RAN function: a RAN function that is offered to dApps over E3. It is named by an E3 RAN function id. Do not confuse it with the E2 RAN function.
  • Sequence id: the identifier of one detection-to-mitigation procedure. The dApp assigns it. Every later message of the procedure carries it unchanged.

General

Notations

For the purposes of the present document, the following notations apply:

  • A service name is written in upper case characters, followed by the word "service". Example: REPORT service.
  • A procedure name is written with the first letter of each word in upper case, followed by the word "procedure". Example: RIC Control procedure.
  • A message name is written in upper case, followed by the word "message". Example: RIC CONTROL REQUEST message.
  • An information element name is written with the first letter of each word in upper case and in italic font, followed by the abbreviation "IE". Example: RAN Function Definition IE.
  • A value of an information element is written between quotation marks. Example: "Value".
  • An ASN.1 type or field name is written in a monospaced font.

Forwards and backwards compatibility

The ASN.1 types of this service model are extensible. A decoder shall ignore extension additions that it does not know. A sender shall not set the extension bit of a type until this specification defines the additions. A change of the grammar that alters the APER encoding of an existing message is a change of the E2 RAN function revision.
